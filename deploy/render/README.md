# 9Router on Render Free with encrypted recovery

Fork: https://github.com/nocodeknow/9router

This fork wraps the upstream server in `deploy/render/run.mjs`. Before starting the server it restores a snapshot from a private Hugging Face dataset; while running it uploads AES-256-GCM encrypted snapshots every five minutes. A consistent SQLite online backup includes committed WAL changes and is integrity-checked. Small machine identity files are included to retain existing API-key identities.

This is snapshot recovery, not live remote database persistence. Abrupt shutdown can lose changes since the last successful upload. Failed uploads increase that window. A best-effort final snapshot runs after the child server exits, but cannot protect against forced container termination.

## Deploy a new service

Open https://render.com/deploy?repo=https://github.com/nocodeknow/9router and use the repository's `render.yaml` on branch `master`. Select the free service. No disk or paid database is created. Existing FreeLLMAPI/OmniRoute services are untouched.

Three secrets need your input:

| Render variable | Value |
| --- | --- |
| `INITIAL_PASSWORD` | A new strong dashboard password |
| `NINEROUTER_BACKUP_TOKEN` | A current Hugging Face fine-grained token with read/write access to `Experiment1213/freellmapi-state` |
| `NINEROUTER_BACKUP_KEY` | A new 64-character hex value generated with `openssl rand -hex 32` |

Keep the dataset **private**. The existing dataset can be reused because the backup filename is **`9router.db.backup`**, not FreeLLMAPI's `freellmapi.db.backup`. The encryption format also rejects snapshots from the wrong application. Do not reuse secrets previously pasted into chat.

`JWT_SECRET`, `API_KEY_SECRET`, and `MACHINE_ID_SALT` are generated by the Blueprint. Keep all these secrets, and the backup key, stable across restarts and deployments. Save them securely; losing them can break authentication or backup recovery. The backup does not contain the environment secrets.

The Blueprint sets `NINEROUTER_BACKUP_ALLOW_EMPTY=1` for a new deployment. It allows the FIRST startup when the remote file is not there yet. An invalid token, non-404 remote error, invalid snapshot or wrong encryption key always blocks startup. Existing local databases are not overwritten.

## Verify before relying on it

1. Deploy, sign into the dashboard and save a harmless preference. Accessing the dashboard initializes the database. Add provider accounts only after verifying the mechanism if possible.
2. Wait for `[9router-backup] encrypted snapshot uploaded` in Render logs. The first attempt runs ten seconds after launch, then every five minutes. If no DB exists yet, no snapshot is uploaded.
3. In Hugging Face confirm `9router.db.backup` exists and has a recent update. Download a private recovery copy before the restart test; retain the matching encryption key.
4. After a verified upload, set `NINEROUTER_BACKUP_ALLOW_EMPTY=0` in Render. This triggers a restart/deploy. On a fresh filesystem expect `[9router-backup] restored encrypted database and identity`. Missing snapshots will now block startup rather than start fresh and overwrite recovery data.
5. Confirm your dashboard login, preference, saved connections and endpoint API keys still work. A 200 from `/api/health` alone does not prove restore.
6. Set `BASE_URL` and `NEXT_PUBLIC_BASE_URL` to the actual HTTPS Render service URL if needed for your chosen OAuth/cloud integrations. Do not guess the hostname. Provider-specific OAuth callbacks/device flows still need testing.

## Scope and limits

Snapshots include the complete main SQLite database (`DATA_DIR/db/data.sqlite`) plus `machine-id`, `auth/cli-secret` and an existing `jwt-secret` file. They do not include downloaded runtimes, MITM certificates, tunnel binaries/state, external CLI home directories or log files outside the database. Use this as a gateway, not as a persistent remote development machine. Only one service may own this snapshot destination; do not start two writers.

The SQLite snapshot has a 32 MiB size ceiling, and the decoded manifest/download have bounded sizes to protect a small free instance. Keep request logging/observability off unless you plan to manage database growth. Snapshots are versioned commits on Hugging Face, so monitor repository history/storage and API limits. No promise of unlimited free storage or uptime is made.

Render Free can sleep or restart, has shared free-hour/resource/bandwidth limits and can restrict heavy outbound API traffic. This fork does not add a keepalive cron; sleeping is safe only up to the last successful snapshot. Never point the FreeLLMAPI keepalive at an unverified 9Router deployment. A paid Render service with a disk is still the straightforward option for local durability.

## Validation

Run `node --test deploy/render/*.test.mjs` on Node 22.23.4+ (uses built-in `node:sqlite`). Tests cover a live WAL-backed SQLite round trip, AES-GCM tampering/wrong-key rejection, mocked HF upload/download, first-start behavior, remote auth failure, corrupt SQLite, destination restrictions and failed upload. A real HF/Render end-to-end restore test still requires your configured service and current credentials.
